# CI and documentation

Forge uses **ordinary GitHub-hosted Ubuntu 24.04 x86-64 runners**. There are no self-hosted runner, larger-runner, or private server requirements. Docker builds the AlmaLinux 9 payload on the GitHub-hosted runner.

The repository has independent workflows:

| Workflow | Responsibility |
| --- | --- |
| `forge-ci.yml` validate | Jess strict/style, embedded-asset verification, source/JPK tests, compile Forge ELF, compiled integration |
| `forge-ci.yml` site | After validation, invokes StroggForge `modGlobalBuild.yml@v69` to validate, render, check links, and deploy Pages |
| `forge-toolchain.yml` | Builds/qualifies the AlmaLinux 9 builder image and publishes to GHCR |
| `das-uberbranch.yml` | Every four hours, builds OpenMW, runs GoogleTests and distro smoke tests, then publishes verified artifacts |

## Documentation is generated by Jess, not Zola

The site follows the [Dreamwind](https://github.com/DreamWeave-MP/dreamwind) pattern. `jess-workspace.toml` names `org.dreamweave.mod-template` as a **dev-dependency**; `jess.lock` pins that package and its `org.dreamweave.site` and `org.dreamweave.theme` dependencies. Source content lives directly under `content/` with `content/home/mod.toml` and `config.toml`. No Zola binary, custom template renderer, or one-off Markdown copying script is used.

The shared workflow currently uses Jess **v0.2.2 for site generation**, independently of the **`JESS_RELEASE_TAG`** that Forge validation requires. That is intentional: Forge itself depends on newer Jess APIs and must **not** be downgraded to the documentation builder runtime. `rust_release: true` instructs the site workflow not to publish a second, potentially incompatible Forge application archive. Forge's Linux executable and `das-uberbranch` remain owned by their respective build/release workflows.

The canonical documentation Markdown is in `content/home/docs/`; edit it there. Locally, after installing Jess and restoring the pinned site packages:

```sh
jess workspace sync --locked
jess workspace run --trusted dreamweave-check
jess workspace run --trusted dreamweave-build -- https://dreamweave-mp.github.io/openmw-forge/
jess workspace run --trusted dreamweave-site -- public https://dreamweave-mp.github.io/openmw-forge/
jess workspace run --trusted dreamweave-links -- public https://dreamweave-mp.github.io/openmw-forge/
```

The first site command validates `mod.toml`; the second prepares the site's metadata; the third renders it into `public/`; the fourth validates local links, assets and anchors. **The `public/` directory is generated; never commit it.**

For GitHub Pages, use **Settings → Pages → Build and deployment → GitHub Actions**. The shared workflow deploys the generated site on the repository's default branch and validates site changes in pull requests without publishing them.

## Forge CI runtime

Set repository variable `JESS_RELEASE_TAG` to a Jess development release containing Forge's required APIs (currently `dev`, which is mutable). The validation workflow installs that Jess runtime and restores pinned site dev-dependencies with `jess workspace sync --locked` before running the Forge gates. The site workflow independently pins its own Jess version via StroggForge `v69`.

## Scheduled release

OpenMW fork/branch selection belongs in `ci/uberbranch-config.jsl`. The [scheduled release documentation](@/home/docs/release.md) covers permissions, cache reuse, and `das-uberbranch` publishing.

The first actual Docker/vcpkg/Qt/OpenMW build remains unqualified until the hosted workflow runs successfully. Do not confuse site success or synthetic ELF tests with a production OpenMW release.
